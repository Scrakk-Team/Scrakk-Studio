# i18n

The UI is translated with **static catalogs**: there is no translation at
runtime. Components call `t('area.key')`, which resolves against the active
language and falls back to the base (`es`). All the text is written in Spanish
first; other languages are generated from it.

## Where the pieces live

| Path | Role |
|---|---|
| `src/shared/i18n/engine.ts` | Pure functions: `translate`, `interpolate`, plural, fallback |
| `src/shared/i18n/index.ts` | Active-locale state, `t`, `translateKey`, locale detection |
| `src/shared/i18n/types.ts` | `LOCALES = ['es', 'en']`, `Locale`, `MessageKey` inputs |
| `src/shared/i18n/catalogs/` | `catalogs/<locale>/<area>.json` + generated `index.ts` |
| `src/shared/i18n/state/<locale>.json` | Per-key source hash and review flags |
| `src/renderer/src/core/i18n/index.ts` | React bridge: `useT`, `initI18n`, `msg` |
| `tools/i18n.mjs` | The catalogs CLI (`npm run i18n`) |
| `tools/i18n-extract.mjs` | One-pass UI extraction (`npm run i18n:extract`) |

`src/shared/i18n` has no React, DOM or Electron imports, so both the renderer
and the main process translate. The main process registers
`ipcMain.on(I18N_IPC.setLocale, …)` in `src/main/index.ts` and calls the shared
`setLocale`, so its dialogs and errors follow the chosen language.

## Catalogs

A catalog is a **flat** JSON object (`clave → texto`) per area. `es` is the
source of truth and is written by hand; every other language is a directory
under `catalogs/`. The areas today are `activitybar`, `app`, `appearance`,
`chat`, `common`, `core`, `explorer`, `extensionviews`, `features`, `git`,
`greetings`, `layout`, `main`, `misc`, `modals`, `onboarding`, `palette`,
`providers`, `services`, `settings`, `social`, `statusbar`, `titlebar`.

`catalogs/index.ts` is **generated**: it imports every area of every locale,
spreads them into `esCatalog` / `enCatalog`, and derives the key type:

```ts
type RawKey = keyof typeof esCatalog

type PluralBase<K extends string> = K extends `${infer Base}.one`
  ? Base
  : K extends `${infer Base}.other`
    ? Base
    : never

export type MessageKey = RawKey | PluralBase<RawKey & string>
```

Because `t` takes a `MessageKey`, a typo does not compile. Do not edit this file
by hand; regenerate it with `npm run i18n -- --sync`.

## The engine

`engine.ts` is pure and never touches state. `translate()` searches, in order:
`<key>.one`/`<key>.other` in the requested locale (when `vars.count` is set),
then `<key>` in that locale, then both in the base locale. If nothing matches it
returns the key itself with `missing: true`. Placeholders
use `{name}`; a placeholder with no value is left intact so the error is visible.
A `TranslateResult` also carries `fellBackToBase` and the `resolvedKey` actually
used. `src/shared/i18n/index.ts` layers the active locale on top:

```ts
export const BASE_LOCALE: Locale = 'es'

export function t(key: MessageKey, vars?: Vars): string {
  const result = translateKey(key, vars)
  if (result.missing && missingReporter) missingReporter(key, currentLocale)
  return result.text
}
```

`detectSystemLocale()` prefers `es` then `en` from `navigator.languages`, and
falls back to `es`. `resolveLocale('system')` uses it.

## In React

`@core/i18n` is the renderer bridge. `useT()` subscribes with
`useSyncExternalStore` so a language change re-renders every consumer:

```tsx
import { t, useT } from '@core/i18n'

const tr = useT()        // hook: re-renders on locale change
tr('settings.skills')    // hook form
t('settings.skills')     // module form, for non-React code
```

`initI18n()` runs once in `main.tsx` and applies the persisted preference (from
`@services/storage`). `setLocalePreference('system' | 'es' | 'en')` persists the
choice, updates `document.documentElement.lang`, and notifies the main process
via `api.i18n.setLocale` (`services/api`). `msg(keyOrText)` resolves a key that was
registered once (for example a command title) or returns the literal unchanged.

## Adding a string

1. Use `t('area.key')` where the text appears.
2. Add `"area.key": "Texto en español."` to `src/shared/i18n/catalogs/es/area.json`.
3. Regenerate the index and translate:

```bash
npm run i18n -- --sync                    # rewrite catalogs/index.ts
npm run i18n -- --status                  # coverage per language
npm run i18n -- --translate en --provider deepl
npm run i18n -- --review en               # markdown table to review
npm run i18n -- --check --strict          # fail if anything is missing/stale
```

`npm run i18n:extract` is the bulk path: `node tools/i18n-extract.mjs` walks
`src/renderer/src` and `src/main` with `@babel/parser`, derives a stable key from
each UI string, and (with `--apply`) writes the new keys into `es`. It skips
data/model areas (the `DENY` list) and is idempotent.

## Tooling

`tools/i18n.mjs` (real flags from its `HELP`):

| Flag | What it does |
|---|---|
| `--status` | Missing / stale / unreviewed per language |
| `--extract` | Keys used in code vs declared in `es` |
| `--sync` | Prunes keys no longer in the base and regenerates `index.ts` |
| `--translate <lang>` | Translates missing/stale (`--provider deepl\|argos`, `--only`, `--limit`, `--force`, `--dry-run`) |
| `--review <lang>` | Markdown table `es` → target of what needs review |
| `--approve <lang> --all` | Clears `needsReview` |
| `--check [--strict]` | Validates state; `--strict` exits non-zero |
| `--doctor` | Checks the DeepL key and quota |

Translation uses **DeepL** by default (`DEEPL_API_KEY` in `.env`); `--provider
argos` uses a local `argostranslate`. A curated `glossary.json` pins exact
strings before the engine sees them. State lives in
`src/shared/i18n/state/<locale>.json` with, per key, `src` (hash of the `es`
text), `area`, `machine` and `needsReview`. **`stale` is never stored**: it is
derived as `hash(es[key]) !== state[key].src`.

## Limits

- `LOCALES` is `['es', 'en']`: only Spanish and English exist today.
- No runtime translation and no interpolation library: only `{name}` placeholders.
- In CI the i18n check is a **warning**; only the release workflow makes it
  blocking (`--check --strict`). See [Contributing](contributing.md).
- `i18n-extract.mjs` needs real dependencies installed, because it loads
  `@babel/parser` from the Vite devDependencies.
- The extractor **denies** some trees on purpose (editor, lsp, debug, `services/ai`,
  `core/i18n`, …); strings there are not migrated automatically.
